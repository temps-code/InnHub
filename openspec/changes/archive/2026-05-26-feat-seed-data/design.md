# Design: Seed Data for MVP Validation

## Technical Approach

Two-step process: (1) `scripts/setup-demo-users.sh` creates 10 auth users via InsForge REST API (`POST /api/auth/users`), outputting a UUID mapping JSON. (2) `scripts/seed.sql` inserts public tables (`properties`, `profiles`, `rooms`, etc.) via `INSERT ... ON CONFLICT DO NOTHING` with deterministic hardcoded UUIDs for all public entities. Teardown script (`scripts/seed-teardown.sql`) reverses public data by property slug. Documentation at `docs/seed-data.md`.

## Architecture Decisions

| Decision | Options | Tradeoffs | Choice |
|---|---|---|---|
| Auth user IDs | Auto-generated vs hardcoded | InsForge write-protects auth schema; must use REST API which generates UUIDs | Auto-generated via REST API |
| Idempotency | `ON CONFLICT DO NOTHING` vs `DELETE + INSERT` | DELETE risks cascading data loss; ON CONFLICT is safe re-run | `ON CONFLICT DO NOTHING` |
| Single file vs per-section | One `.sql` vs multiple | Single file simplifies one-shot execution; sections via comments | Single file, section comments |
| Auth user creation | REST API vs SQL INSERT | SQL INSERT on auth schema blocked by InsForge; REST API works but returns auto-generated UUIDs | REST API (`POST /api/auth/users`) |
| Existing data coexistence | Use existing property vs create new | Existing property has real admin email; seed needs clean demo scope | Create new properties with distinct UUIDs |

## Data Flow

```
setup-demo-users.sh ─── REST API (POST /api/auth/users) ─── 10 auth users ─── UUID mapping JSON
       │
       ▼
run-raw-sql(seed.sql)
  │
  ├─ Section 1: properties ─────────────────────┐  (2 properties, no FK)
  ├─ Section 2: profiles ───────────────────────┤  (FK: auth_user_id from JSON, property_id)
  ├─ Section 3: room_types ─────────────────────┤  (FK: property_id)
  ├─ Section 4: rooms ──────────────────────────┤  (FK: room_type_id, property_id)
  ├─ Section 5: guests ─────────────────────────┤  (FK: property_id)
  ├─ Section 6: reservations + items ───────────┤  (FK: guest, room_type, room, property)
  ├─ Section 7: stays + stay_guests ────────────┤  (FK: reservation_item, room, guest)
  ├─ Section 8: invoices + payments ────────────┤  (FK: guest, reservation, stay)
  ├─ Section 9: housekeeping_tasks ─────────────┤  (FK: room, profile, property)
  ├─ Section 10: maintenance_tickets ───────────┤  (FK: room, profile, property)
  └─ Section 11: room state updates ────────────┘  (UPDATE based on active stays + tickets)
```

## Data Architecture

### UUID Scheme
- Public table UUIDs are hardcoded constants — deterministic, no `gen_random_uuid()`.
- Prefix convention for readability: `00000000-0000-0000-0000-{nnnnnnnnnnnn}` where `nnnnnnnnnnnn` encodes domain + index.
- Auth user IDs are auto-generated by InsForge REST API, stored in `scripts/demo-user-uuids.json`.
- Property IDs: `00000000-0000-0000-0010-0000000000{01..02}`
- Profile IDs: `00000000-0000-0000-0011-{property_prefix}000{01..05}`
- Room type IDs: `00000000-0000-0000-0020-{property_prefix}00{01..03}`
- Room IDs: `00000000-0000-0000-0030-{property_prefix}{room_suffix}`
- Guest IDs: `00000000-0000-0000-0040-{property_prefix}00{01..04}`
- Reservation/Item/Stay IDs: `00000000-0000-0000-0050-{nnnnnnnnnnnn}`
- Invoice/Payment IDs: `00000000-0000-0000-0060-{nnnnnnnnnnnn}`
- Task/Ticket IDs: `00000000-0000-0000-0070-{nnnnnnnnnnnn}`

### Teardown Pattern

```sql
-- Reverse order: operations → billing → stays → reservations → guests → rooms → room_types → profiles → properties
-- Auth users are NOT deleted via SQL (write-protected by InsForge)
DELETE FROM maintenance_tickets WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM housekeeping_tasks WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM payments WHERE invoice_id IN (SELECT id FROM invoices WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos')));
DELETE FROM invoices WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM stay_guests WHERE stay_id IN (SELECT id FROM stays WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos')));
DELETE FROM stays WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM reservation_items WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM reservations WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM guests WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM rooms WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));
DELETE FROM room_types WHERE property_id IN (SELECT id FROM properties WHERE slug IN ('hotel-tarija', 'hostal-los-chapacos'));

```

## Interfaces / Contracts

No new TypeScript interfaces. The scripts interact solely with the database schema defined in `001_define_core_innhub_schema.sql` and `auth.users`. The `email LIKE '%@innhub.dev'` pattern is the contract between seed and teardown.

## Execution Contract

Two-step process:
1. Create auth users via API: `bash scripts/setup-demo-users.sh` (requires `INSFORGE_URL` env var)
2. Seed public tables via SQL: `insforge_run-raw-sql(query: "<contents of seed.sql>", apiKey: "<admin-key>")`

Requires: `INSFORGE_URL` environment variable, InsForge admin API key for SQL, existing schema from migration `001_define_core_innhub_schema.sql`.

## Testing Strategy

| Layer | What to Test | Approach |
|---|---|---|
| Auth | Login with each demo account | After seed, call `signInWithPassword(email, 'Demo123!')` for all 10 users — all MUST succeed |
| Auth | Password hash correctness | Validate via InsForge auth, not direct SQL comparison |
| Idempotency | Re-run seed | Execute seed twice — second run MUST produce 0 new rows and 0 errors |
| Idempotency | Teardown + re-seed | Run teardown, then seed — MUST produce same data as first run |
| Data integrity | All FK references | Query each domain table — every `property_id` MUST reference a seed property, every FK chain MUST resolve |
| Verification | Manual row count audit | Run verification queries from `docs/seed-data.md` and compare against expected counts |

## Migration / Rollout

No migration required. Seed script is post-schema data population. Run after `001_define_core_innhub_schema.sql` has been applied. Rollback via `scripts/seed-teardown.sql`.

## Open Questions

None — schema is confirmed, auth table structure is verified via `information_schema`, and existing data UUIDs are known to avoid conflicts.
